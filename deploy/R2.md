# Cloudflare R2 — ছবি আর কাগজ ডাটাবেসের বাইরে

আগে সব ছবি base64 লেখা হয়ে PostgreSQL-এর ভেতরে থাকত। এখন R2 চালু থাকলে ছবির আসল bytes যায় R2-এর **private bucket**-এ,
আর ডাটাবেসে থাকে শুধু একটা চাবি (key) — সাথে আকার, ধরন (content type) আর sha256 (`stored_objects` টেবিল)।
অ্যাপ (২.৩৪.x) আর Vue ওয়েবের কিছুই বদলাতে হয়নি: তারা আগের মতোই base64 পাঠায়, আর সার্ভার আগের মতোই **হুবহু একই base64 লেখা**
ফেরত দেয় (R2 থেকে পড়ে, মেমোরি-cache সহ)। কোনো public লিংক নেই — bucket-এ সরাসরি কেউ ঢুকতে পারে না।

| কোন ছবি | আগে (base64) | এখন (R2 চালু থাকলে) |
|---|---|---|
| প্রোফাইলের ছবি আর ছোট ছবি (thumb) | `user_profiles.photo`, `photo_thumb` | `photo_key`, `photo_thumb_key` |
| যাচাইয়ের কাগজের ছবি (লাইসেন্স, সার্টিফিকেট, গাড়ি…) | `verify_docs.data` | `verify_docs.storage_key` |
| ল্যাব রিপোর্টের ছবি | `lab_report_photos.data` | `lab_report_photos.storage_key` |

Migration: `backend/src/main/resources/db/migration/V602__r2_files.sql`। কোড: `backend/…/common/StoredFiles.kt`,
`StorageMigrator.kt`, `ObjectStorage.kt`।

## ১. চালু/বন্ধ (feature flag)

নিচের env var-গুলো **সব** থাকলে R2 চালু, একটাও না থাকলে বন্ধ — বন্ধ থাকলে আচরণ আগের মতোই হুবহু (ছবি base64 হয়ে ডাটাবেসে)।
তাই secret বসানোর আগেই এই কোড main-এ গেলেও কিছু ভাঙে না।

| env var | কী | কোথা থেকে |
|---|---|---|
| `R2_ENDPOINT` (পছন্দের) **বা** `R2_ACCOUNT_ID` | পুরো endpoint `https://<id>.r2.cloudflarestorage.com` — ড্যাশবোর্ডে যেমন দেখায় শেষে `/<bucket>` সহ দিলেও চলে (সার্ভার ওটা বাদ দেয়); দুটোই থাকলে `R2_ENDPOINT`। শুধু account id দিলে ঠিকানা নিজেই বানায় | Cloudflare → R2 → bucket → Settings → S3 API |
| `R2_ACCESS_KEY_ID` | R2 API token-এর Access Key ID | R2 → Manage API tokens → Create (Object Read & Write, শুধু এই bucket) |
| `R2_SECRET_ACCESS_KEY` | ওই token-এর Secret Access Key | একই জায়গায় (একবারই দেখায়) |
| `R2_BUCKET` | bucket-এর নাম (যেমন `lifolo-files`) — **public access বন্ধ** রাখুন | R2 → Create bucket |
| `R2_REGION` (ঐচ্ছিক) | খালি = `auto` (R2-এর জন্য ঠিক); শুধু MinIO-র মতো অন্য S3-এ লাগে | — |
| `R2_CACHE_MB` (ঐচ্ছিক) | R2 থেকে পড়া ছবির মেমোরি-cache, প্রতি সার্ভার (ডিফল্ট ৬৪) | — |

**Deploy-এ কী লাগবে:** `deploy/deploy-backend.sh` আর `.github/workflows/deploy-backend.yml` আগে থেকেই এই পাঁচটা নাম
(`R2_ACCOUNT_ID`, `R2_ENDPOINT`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`) GitHub secret থেকে
`/etc/lifolo/app.env`-এ লেখে — GitHub-এ secret চারটা এখন আছে (`R2_ENDPOINT`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET=lifolo-files`, private);
deploy সেগুলো `/etc/lifolo/app.env`-এ পৌঁছে দিলেই R2 চালু। `R2_REGION`/`R2_CACHE_MB` লাগলে সেগুলো ওই তালিকায় যোগ করতে হবে (এখন লাগে না)।
deploy-status-এ `r2 on` দেখাবে (শুধু `R2_BUCKET` দেখে — বাকিগুলোও আছে কি না নিজে দেখে নিন)।

## ২. নতুন ছবি, পড়া আর মোছা

* **লেখা:** যাচাই আগের মতোই (আকার: প্রোফাইল ≤ ৬০০ KB / thumb ≤ ১০০ KB base64, কাগজ ≤ ৭০০ KB আর JPEG/PNG, ল্যাব রিপোর্ট
  ≤ ৩০০ KB আর ≤ ২টা)। তারপর R2-এ upload, ডাটাবেসে চাবি। ঠিকঠাক base64 হলে bucket-এ আসল ছবি (`.jpg`/`.png`); অদ্ভুত লেখা
  (padding ছাড়া, ফাঁকা জায়গা/নতুন লাইনসহ) হলে লেখাটাই (`.b64.txt`) — যাতে ফেরত সবসময় হুবহু একই আসে।
  ডাটাবেসের কাজ বাতিল (rollback) হলে upload করা ফাইলও মুছে যায়।
* **পড়া:** আগে পুরোনো কলাম (এখনো সরানো হয়নি এমন সারি), না থাকলে চাবি দিয়ে R2। R2 না পেলে/ভুল হলে ছবি "নেই"-এর মতো দেখায়
  আর Sentry-তে ভুল যায় (পুরো অনুরোধ ভাঙে না)।
* **মোছা:** কোনো সারি থেকে চাবি চলে গেলে (সারি মোছা — অ্যাকাউন্ট মোছা, তালিকা সরানো, নতুন রিপোর্ট, ডেমো মোছা, ON DELETE CASCADE সহ —
  বা নতুন ছবি দিয়ে বদলানো) ডাটাবেসের trigger একই transaction-এ চাবিটা `stored_objects_trash`-এ রাখে। প্রতি মিনিটে JobRunr-এর
  কাজ `storage-trash` R2 থেকে সেগুলো মোছে (ব্যর্থ হলে পরে আবার, ৫০ বার পর্যন্ত — `attempts`, `last_error`)।

## ৩. পুরোনো base64 ছবি R2-এ সরানো (একবারের কাজ)

সহজ পথ: Actions → **"R2 migrate"** → Run workflow (`.github/workflows/r2-migrate.yml` → VPS-এ `deploy/ci/r2-migrate.py`)।
এটা নিচের লুপটাই চালায়, আর আগে-পরে `GET /api/cron/storage/probe` দিয়ে প্রতি ধরনের একটা সারি মিলিয়ে দেখে: সরানোর আগে API যে
base64 ফেরত দিত আর পরে (R2 থেকে পড়ে) যা দেয় — দুটোর sha256 একই কি না। ফল শুধু সংখ্যা: Summary আর `ci-log-r2-migrate`।

হাতে করতে চাইলে, secret বসিয়ে deploy করার পর, VPS-এ (`CRON_SECRET` থাকে `/etc/lifolo/app.env`-এ):

```bash
S=$(sudo grep '^CRON_SECRET=' /etc/lifolo/app.env | cut -d= -f2-)
curl -s -H "Authorization: Bearer $S" http://127.0.0.1:8088/api/cron/storage            # কত বাকি
# একবারে ২০০টা করে, বাকি ০ না হওয়া পর্যন্ত (যতবার খুশি চালানো যায়, মাঝপথে থামালেও ক্ষতি নেই)
while :; do
  r=$(curl -s -X POST -H "Authorization: Bearer $S" "http://127.0.0.1:8088/api/cron/storage/migrate?limit=200"); echo "$r"
  echo "$r" | grep -q '"migrated":0,' && break
done
```

প্রতিটা সারির জন্য: upload → R2 থেকে আবার পড়া → **sha256 মিললে তবেই** এক transaction-এ চাবি বসানো আর base64 কলাম খালি করা
(আর শুধু যদি সারিতে তখনো সেই একই ছবি থাকে — মাঝে কেউ ছবি বদলালে upload মুছে পরের বার আবার)। না মিললে/ভুল হলে ছবি ডাটাবেসেই থাকে,
উত্তরে `failed` বাড়ে। উত্তর: `{migrated, failed, changed, configured, remaining: {profilePhoto, profileThumb, verifyDocs,
labReportPhotos}, stored, trash}`। একসাথে দুটো চললে 409; R2 বন্ধ থাকলে 400।

`failed` শূন্য না হলে সার্ভারের লগ/Sentry দেখুন ("R2 migration: …")। সব শেষে ডাটাবেস ছোট করতে চাইলে (ঐচ্ছিক):
`VACUUM (FULL, ANALYZE) user_profiles, verify_docs, lab_report_photos;` (চলার সময় টেবিল লক থাকে — রাতে)।

ডেমো জগৎ (`admin_demo_seed`) এখনো ছোট base64 ছবি সরাসরি ডাটাবেসে লেখে; migration চালালে সেগুলোও সরে, ডেমো মুছলে R2 থেকেও মোছে।

## ৪. সাবধান

* R2 চালুর পর **R2_* সরিয়ে দেবেন না**: তখন যে ছবিগুলো R2-এ আছে সেগুলো আর পড়া যাবে না ("নেই" দেখাবে, ডাটাবেসের চাবি থেকে যায়;
  secret ফিরিয়ে দিলেই আবার আসে)। নতুন ছবি তখন আবার ডাটাবেসে যাবে।
* Bucket-এ lifecycle/মোছার নিয়ম দেবেন না — কোনটা মুছবে তা সার্ভারই ঠিক করে।
* Backup: PostgreSQL-এর backup-এ এখন শুধু চাবি থাকে; ছবির backup R2-এর দিকে (দরকার হলে R2 → অন্য bucket-এ copy)।
* টেস্ট: CI-তে Testcontainers-এর MinIO (`backend/src/test/kotlin/com/lifolo/common/R2StorageIT.kt`); R2 ছাড়া আচরণ
  `StorageOffIT.kt` আর বাকি সব টেস্ট।
